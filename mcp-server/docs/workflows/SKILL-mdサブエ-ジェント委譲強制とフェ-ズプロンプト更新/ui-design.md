# UI設計: SKILL.mdサブエージェント委譲強制とフェーズプロンプト更新

## サマリー

本タスクはドキュメント変更のみのタスクであり、UIコンポーネントや画面設計の変更は含まれない。SKILL.mdとREADME.mdは、ワークフロー実行時にメインClaudeが読み込むドキュメントであり、「情報設計」の観点からの改善となる。このUIデザイン文書では、ドキュメント構造の再編成がワークフロー利用者（メインClaudeエージェント）の理解を促進する方法を分析する。

## UI変更の有無

### UIコンポーネント変更: なし
本タスクはWebアプリケーションやコンポーネントUIの実装を伴わない。ボタン、フォーム、モーダル、ナビゲーションなどのUIエレメントの追加・変更はない。

### 画面設計変更: なし
ユーザーに見える画面や視覚的なインターフェース変更はない。CLIコマンド（`/workflow`）の実行結果表示形式に変更はない。MCPサーバーのツール定義も変更されない。

### MCPツール変更: なし
既存のMCPツール（`workflow_start`, `workflow_next`, `workflow_status`等）のシグネチャ、パラメータ、戻り値に変更はない。

## ドキュメント構造の変更と情報設計

本タスクで行われるドキュメント変更は、**情報設計の観点**から以下のような改善をもたらす。

### 1. Orchestratorパターンセクションの新規追加

SKILL.mdに「Orchestratorパターン」セクションを「フェーズ構成（19フェーズ）」の直後に配置することで、ユーザー（メインClaude）のメンタルモデルの形成を支援する。

**Orchestratorパターンの情報設計効果:**

- **認知的階層の明確化**: フェーズ構成で「19フェーズが存在する」という事実を知った直後に、「メインClaudeがどのようにこれらフェーズを実行するべきか」という実行パターンを説明することで、全体像の理解が深まる。

- **ナレーティブフロー**: ドキュメント読者が自然な思考フロー（「フェーズは何か」 → 「どのように実行するか」 → 「詳細ルール」）に沿って理解を進められるようになり、ジャンプして読む場合の参照ポイントも明確になる。

- **ビジュアルまたはテキストフロー図**: Orchestratorパターンセクションには文字ベースのフロー図が含まれ、メインClaudeが自身の責務範囲（タスク開始・フェーズ委譲・次フェーズ進行）を瞬時に把握できる。

### 2. フェーズ別subagent設定テーブルの追加

21フェーズとそれぞれのsubagent_type、model、入出力ファイルを一覧にしたテーブル（約25行）を追加することで、参照性が大幅に向上する。

**設定テーブルの情報設計効果:**

- **スキャナビリティ**: テーブル形式により、特定フェーズの設定をキーワード検索（Ctrl+F）で素早く見つけることができる。従来の段落形式では、フェーズ説明を読み込む必要があった。

- **一貫性の可視化**: 全21フェーズが同じテーブル構造で並べられることで、「あるフェーズはsonnet + general-purpose、別のフェーズはhaikuだ」といった整合性をチェックしやすくなる。

- **プリンシプルの顕在化**: 軽いフェーズ（build_check, code_review）とそれ以外のフェーズでmodel（haiku/sonnet）や出力ファイルが異なることが、表の行を比較することで一目瞭然になり、設計原則が暗黙知から形式知に変わる。

### 3. subagent起動テンプレートとサマリー必須化指示

SKILL.mdに「subagent起動テンプレート」を追加し、Task tool呼び出しの標準形式を示す。同時に「成果物の先頭に## サマリーセクション（50行以内）を配置すること」をテンプレートに明記。

**起動テンプレートの情報設計効果:**

- **実行例の具体化**: メインClaudeが「Task toolをどのような形式で呼び出すべきか」を迷うことなく、テンプレートをコピー・ペーストしたうえで値を埋めるだけで実行できるようになる。認知負荷が軽減される。

- **次フェーズへのコンテキスト引き継ぎの効率化**: サマリー必須化指示によって、次フェーズのsubagentが「5000行の仕様書全文」ではなく「50行のサマリー」を読み込むだけで十分なコンテキストを得られるようになり、トークン効率が向上する（これはメインClaudeではなく、subagentの認知負荷軽減だが、メインClaudeの指示品質向上につながる）。

- **暗黙的な慣例の明示化**: 従来「サマリーを書くのが習慣」だったが、テンプレートに明記することで「サマリーを書くのは必須」に昇格し、compliance率が高まる。

### 4. 並列フェーズ実行例の追加

SKILL.mdに「並列フェーズの実行例」を追加し、`parallel_analysis`での複数Task同時起動方法を具体的に示す。

**並列実行例の情報設計効果:**

- **実装パターンの提示**: メインClaudeが「複数のTask toolを同時に起動する」という動作を、文章的な説明ではなく、実際のコード例（Task呼び出し × 2 + workflow_complete_sub × 2 + workflow_next）で理解できるようになり、誤実行の可能性が低くなる。

- **並列フェーズへの心理的ハードルの低減**: 従来「並列フェーズ」が複雑だと感じられていたが、「複数TaskをAPIのようにバッチ呼び出しして、両方の完了を待機する」という明確なパターンが示されることで、実装の難易度が低く認識される。

### 5. フェーズ構成の「18フェーズ」から「19フェーズ」への更新

SKILL.mdのタイトルとフェーズ順序を更新し、`regression_test`（リグレッションテスト）を`testing`と`parallel_verification`の間に追加。

**フェーズ更新の情報設計効果:**

- **ドキュメント鮮度の向上**: 「18フェーズ」というタイトルが古い（実装はすでに19フェーズ）ことによる違和感が解消され、ユーザーがドキュメントを信頼できるようになる。

- **リグレッションテストの重要性の強調**: 順序図の中に`regression_test`が明示的に記載されることで、「単なるオプション」ではなく「ワークフローの必須ステップ」として認識されるようになり、スキップされるリスクが低減される。

- **フェーズ数の心理的インパクト**: 「18フェーズ」から「19フェーズ」への微増ですら、ドキュメント全体の更新と組み合わせることで「新機能が追加された」という改善感が生まれ、メインClaudeの注意力が向上する。

### 6. README.mdの全文置換による統一化

`.claude/workflow-phases/README.md`を全文置換し、以下を統一する:
- フェーズ一覧（19フェーズ）
- 並列グループ一覧テーブル
- フェーズ順序図
- 各フェーズの責務テーブル（subagent_type, model含む）

**README統一化の情報設計効果:**

- **マスタードキュメント化**: SKILL.mdでは大局的な方針を示し、README.mdではより詳細なフェーズ説明を提供することで、用途に応じたドキュメント分棲が実現される。メインClaudeが「全体像を知りたい」時はSKILL.md、「フェーズ XX の詳細を知りたい」時はREADME.mdと、参照先が明確になる。

- **圧倒的なスキャナビリティ**: フェーズごとの詳細（責務、subagent_type、model、入出力ファイル）が一元化されたテーブルに集約されることで、「フェーズ XX はどのsubagentで実行するのか」という質問への回答が秒単位で可能になる。

- **削除項目の明示的抹消**: `architecture_review`の削除がREADMEに反映されることで、「このフェーズはもう存在しない」ことが明確に周知され、古い情報を参照している可能性が排除される。

## ドキュメント変更による利用体験の向上

### メインClaudeの認知負荷軽減

Orchestratorパターンセクション、subagent設定テーブル、テンプレート、並列実行例が追加されることで、メインClaudeが「どのようにフェーズを委譲すべきか」を迷わずに実行できるようになる。結果として、コンテキスト内の「判断ループ」や「確認ステップ」が削減され、compactingが発生しにくくなる。

### ワークフロー利用者（エンドユーザー）の体験向上

エンドユーザーがワークフロー実行時にメインClaudeからもらうレスポンスの品質が向上する。メインClaudeがSKILL.mdの明確な指示に従うようになるため、「何のフェーズを実行しているか」「次は何を実行するか」といった説明が一貫性を持つようになり、混乱が減少する。

### ドキュメント保守性の向上

SKILL.md、README.md、CLAUDE.mdの3つのドキュメント間での整合性が、セクション追加と一覧表の統一によってより容易に保証されるようになる。今後のフェーズ追加時にも、テーブル行を追加するだけで3つのドキュメントすべてが自動的に同期される（手動で3箇所を編集する）。

## 情報アーキテクチャの改善点

### 階層構造の明確化

従来のSKILL.mdは「ワークフロー使用タイミング」「コマンド」「フェーズ構成」が混在していたが、新たな構成では以下のような明確な階層が生まれる：

1. **高レベル**: フェーズ構成（「19フェーズが存在する」という事実）
2. **次レベル**: Orchestratorパターン（「メインClaudeがどのように実行するか」という戦略）
3. **詳細レベル**: フェーズ別subagent設定（「各フェーズの具体的な設定」）
4. **実装レベル**: テンプレートと例（「実際のコード形式」）

この階層が明確になることで、ユーザーの理解が段階的に深化していく。

### 参照可能性の向上

テーブル、図、具体例が追加されることで、特定の情報へのアクセス時間が短縮される。従来「フェーズ XX の詳細を知りたい」と思った時は、全文を読み込む必要があったが、テーブルのキーワード検索で秒単位で目的の情報に到達できるようになる。

## 制約と非変更領域

本UI設計の対象は**ドキュメント構造のみ**であり、以下の領域は変更されない：

- **ワークフロー状態管理**: JSON形式の状態管理ファイル（`.claude/state/workflows/`）の構造
- **フェーズプロンプト**: 各フェーズの具体的な実行指示（`.claude/workflow-phases/`配下のMarkdownファイル）
- **MCPサーバー実装**: workflow-plugin/mcp-server内のTypeScriptコード
- **ユーザー向け出力**: ワークフロー実行時のメッセージ形式

## ドキュメント設計の哲学

本タスクで採用される情報設計のアプローチは、以下の原則に基づいている：

1. **段階的な詳細化**: 大局（フェーズ構成）から個別（テンプレート）へ段階的に詳細化することで、様々なレベルの読者に対応する。

2. **参照性の最大化**: テーブル、リスト、図を多用することで、ランダムアクセス（特定情報への直接参照）を効率化する。

3. **実装親和性**: コード例、テンプレート、具体的な実行パターンを示すことで、読み手が「読んで理解する」から「読んで即座に実行する」へ移行できるようにする。

4. **整合性の強化**: 複数ドキュメント間での重複と一貫性を明確に管理することで、誤った情報の参照を防ぐ。

これらの原則が実装されることで、SKILL.mdとREADME.mdは単なる「説明書」から「実行ガイド」へと進化する。
